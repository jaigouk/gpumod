To refactor this correctly, we need to ensure that `core.py` acts as the foundation to avoid circular imports (e.g., `priority.py` needs `Job` from `core.py`).

Here is the refactored package structure.

### 1. `queue/core.py`
This module contains the base data structures and the simplest implementation of a queue.

```python
from dataclasses import dataclass, field
from typing import Any, List, Optional
import uuid

@dataclass
class Job:
    payload: Any
    priority: int = 0
    retries: int = 0
    max_retries: int = 3
    id: str = field(default_factory= lambda: str(uuid.uuid4()))

    def __lt__(self, other: 'Job'):
        # Needed for PriorityQueue (heapq) to handle tie-breaking
        return self.priority > other.priority

class JobQueue:
    """A basic FIFO (First-In-First-Out) queue implementation. """
    def __init__(self):
        self._items: List[Job] = []

    def push(self, job: Job) -> None:
        self._items.append(job)

    def pop(self) -> Optional[Job]:
        if not self._items:
            return None
        return self._items.pop(0)

    def __len__(self) -> int:
        return len(self._items)
```

### 2. `queue/priority.py`
This module specializes the queue logic using a heap. It imports `Job` from `core`.

```python
import heapq
from typing import Optional
from .core import Job, JobQueue

class PriorityQueue(JobQueue):
    """A priority-based queue implementation using a min-heap."""
    def __init__(self):
        # We store items in a list used by heapq
        self._items: list[tuple[int, Job]] = []

    def push(self, job: Job) -> None:
        # We use negative priority because heapq is a min-heap 
        # but usually higher numbers = higher priority.
        heapq.heappush(self._items, (-job.priority, job))

    def pop(self) -> Optional[Job]:
        if not self._items:
            return None
        _, job = heapq.heappop(self._items)
        return job

    def __len__(self) -> int:
        return len(self._items)
```

### 3. `queue/retry.py`
This module encapsulates the retry logic. It is decoupled from the specific Queue type so it can work with any Job object.

```python
import time
from typing import Callable, Any
from .core import Job

def process_with_retry(
    job: Job, 
    worker_func: Callable[[Job], Any], 
    initial_delay: float = 1.0,
    max_delay: float = 60.0
) -> Any:
    """
    Executes worker_func with the given job, applying 
    exponential backoff on failure.
    """
    delay = initial_delay
    while True:
        try:
            return worker_func(job)
        except Exception as e:
            if job.retries >= job.max_retries:
                print(f"Job {job.id} failed after {job.max_retries} retries.")
                raise e
            
            print(f"Retrying job {job.id} in {delay}s... (Attempt {job.retries + 1})")
            time.sleep(delay)
            
            job.retries += 1
            delay = min(delay * 2, max_delay)
```

### 4. `queue/__init__.py`
This file defines the public API, making it easy for users to import the main classes without knowing the internal file structure.

```python
from .core import Job, JobQueue
from .priority import PriorityQueue
from .retry import process_with_retry

__all__ = [
    "Job",
    "JobQueue",
    "PriorityQueue",
    "process_with_retry",
]
```

### Key Refactor Improvements:

1.  **Dependency Flow**: The dependency graph is linear: `core` $\rightarrow$ `priority` & `retry` $\rightarrow$ `__init__`. This prevents circular imports.
2.  **Encapsulation**: `JobQueue` and `PriorityQueue` now share a common interface (`push`, `pop`), allowing you to swap implementations easily in your main code.
3.  **Type Safety**: Added type hints (`Optional`, `Callable`, etc.) which were likely missing or messy in a single-file script.
4.  **Clean API**: A user can now simply do:
    ```python
    from queue import PriorityQueue, Job, process_with_retry

    q = PriorityQueue()
    q.push(Job(payload="Task 1", priority=10))
    
    job = q.pop()
    process_with_retry(job, my_worker_function)
    ```
5.  **Complexity Management**: `retry.py` doesn't care how the queue is stored; it only cares about the `Job` object's state, adhering to the Single Responsibility Principle.
