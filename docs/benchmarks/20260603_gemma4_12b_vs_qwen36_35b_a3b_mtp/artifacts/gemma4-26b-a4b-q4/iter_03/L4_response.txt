*   Goal: Fix a concurrency bug in a `JobQueue` implementation.
*   Language: Python.
*   Context: A dictionary `self.jobs` stores pending jobs, and `self.results` stores completed job results.
*   The identified bug: Multiple threads can write to `self.results` simultaneously, and more importantly, the sequence of checking presence in `self.jobs`, reading from it, writing to `self.results`, and deleting from `self.jobs` is not atomic.

    *   `add_job`: Adds to `self.jobs`. While dictionary operations in CPython are often thread-safe due to the GIL, it's bad practice to rely on it for logical atomicity.
    *   `process_job`:
        1.  Checks `if job_id not in self.jobs`.
        2.  Reads `data = self.jobs[job_id]`.
        3.  Executes `processor(data)`. (Note: The actual processing is done *outside* the lock to allow parallelism, which is good).
        4.  Writes `self.results[job_id] = result`.
        5.  Deletes `del self.jobs[job_id]`.
    *   *The Core Issue:* If two threads call `process_job` with the *same* `job_id`, they both might pass the `if job_id not in self.jobs` check before either has deleted it. This leads to the processor running twice for the same job, or one thread deleting the job while another is trying to access it.

    *   The `jobs` and `results` dictionaries need protection.
    *   Specifically, the sequence "Check if job exists -> Get data -> Delete job" must be atomic relative to other threads attempting to process that same job.
    *   *Crucial detail:* Do not hold the lock while calling `processor(data)`. If the processor is slow, holding the lock blocks all other threads from adding or processing jobs.

    *   *Approach A: One giant lock.*
        Lock everything. Problem: `processor(data)` is called inside the lock. This serializes the whole system, defeating the purpose of a job queue.

    *   *Approach B: Fine-grained locking.*
        Use a `threading.Lock` to protect access to the `jobs` and `results` dictionaries.

    *   *Step-by-step logic for `process_job` with locks:*
        1.  Acquire lock.
        2.  Check if `job_id` is in `self.jobs`.
        3.  If not, release lock and return `False`.
        4.  If yes, pop the job from `self.jobs` (this ensures only ONE thread "claims" the job).
        5.  Release lock.
        6.  Run `result = processor(data)`.
        7.  Acquire lock.
        8.  Store `self.results[job_id] = result`.
        9.  Release lock.
        10. Return `True`.

    *   `__init__`: Initialize `self.lock = threading.Lock()`.
    *   `add_job`: Wrap `self.jobs[job_id] = data` in a lock.
    *   `process_job`:
        *   Use `with self.lock:` to check and `pop` from `self.jobs`.
        *   Perform processing outside the `with` block.
        *   Use `with self.lock:` to write to `self.results`.
    *   `get_result`: Wrap `self.results.get(job_id)` in a lock.

    *   `pop(job_id, default)` is safer than `if in: ... del`.
    *   If I use `data = self.jobs.pop(job_id, None)`, I can check if `data` is `None` to see if the job existed. This is atomic within the lock.

        2. If no job, return `False`.
        3. If job, release lock.
        4. Run `processor(data)`.
        5. Lock -> Set `self.results[job_id] = result`.
        6. Release lock.

<content>
To fix the concurrency bug, we need to ensure that the operations on the `jobs` and `results` dictionaries are atomic. 

The primary issue in the original code is that the "check-then-act" sequence (checking if a job exists, retrieving it, and then deleting it) is not atomic. If two threads call `process_job` with the same `job_id` simultaneously, both might pass the `if job_id not in self.jobs` check before either has a chance to delete it. This results in the job being processed twice.

Furthermore, we must **not** hold the lock while executing the `processor(data)` function. If we held the lock during the processing phase, the entire queue would become serialized, meaning only one job could be processed at a time across the entire application, defeating the purpose of concurrency.

Here is the corrected implementation:

```python
import threading

class JobQueue:
    def __init__(self):
        self.jobs = {}
        self.results = {}
        # A single lock to protect access to the internal dictionaries
        self._lock = threading.Lock()

    def add_job(self, job_id, data):
        with self._lock:
            self.jobs[job_id] = data
        return job_id

    def process_job(self, job_id, processor):
        # 1. Atomically "claim" the job.
        # We use pop() inside the lock so that only one thread can 
        # successfully retrieve the data for a specific job_id.
        with self._lock:
            data = self.jobs.pop(job_id, None)
        
        # If data is None, the job didn't exist or was already claimed
        if data is None:
            return False

        # 2. Execute the processor OUTSIDE the lock.
        # This allows other threads to add or process other jobs 
        # while this thread is doing heavy lifting.
        result = processor(data)

        # 3. Atomically store the result.
        with self._lock:
            self.results[job_id] = result
            
        return True

    def get_result(self, job_id):
        with self._lock:
            return self.results.get(job_id)

# --- Example Usage / Testing ---
if __name__ == "__main__":
    import time

    def slow_processor(data):
        time.sleep(0.1)  # Simulate heavy work
        return data * 2

    queue = JobQueue()
    queue.add_job(1, 10)
    queue.add_job(2, 20)

    def worker(job_id):
        success = queue.process_job(job_id, slow_processor)
        print(f"Job {job_id} processed: {success}")

    # Start multiple threads trying to process the SAME job
    # Only one should succeed (return True)
    threads = []
    for _ in range(5):
        t1 = threading.Thread(target=worker, args=(1,))
        t2 = threading.Thread(target=worker, args=(2,))
        threads.extend([t1, t2])

    for t in threads:
        t.start()
    for t in threads:
        t.join()

    print(f"Result for Job 1: {queue.get_result(1)}")
    print(f"Result for Job 2: {queue.get_result(2)}")
```

### Key Changes Made:
1.  **Introduced `self._lock`**: Used `threading.Lock()` to synchronize access to the shared state (`self.jobs` and `self.results`).
2.  **Atomic "Claiming"**: Instead of checking `if in` and then calling `del`, I used `self.jobs.pop(job_id, None)` inside a `with self._lock` block. This is a thread-safe way to check for existence and remove the item in one single, atomic step. If two threads try to `pop` the same ID, only one will get the data; the other will get `None`.
3.  **Granular Locking**: I ensured that the `processor(data)` call is **not** inside the `with self._lock` block. This is critical for performance, as it allows the `JobQueue` to remain highly concurrent while still being thread-safe.
4.  **Thread-safe Reads/Writes**: All access to `self.jobs` (in `add_job` and `process_job`) and `self.results` (in `process_job` and `get_result`) is now wrapped in the lock.
