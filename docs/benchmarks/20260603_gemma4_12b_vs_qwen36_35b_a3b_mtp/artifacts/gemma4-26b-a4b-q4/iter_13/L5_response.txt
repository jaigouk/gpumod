Here is the refactored package structure.

### 1. `queue/core.py`
This module contains the foundational data structures. It has no dependencies on other modules within the package, preventing circular imports.

```python
from dataclasses import dataclass, field
from typing import Any, List

@dataclass(order=False)
class Job:
    """Represents a unit of work."""
    id: str
    payload: Any
    priority: int = 0
    retries: int = 0

class JobQueue:
    """A basic First-In-First-Out (FIFO) job queue."""
    def __init__(self):
        self._queue: List[Job] = []

    def push(self, job: Job) -> None:
        self._queue.append(job)

    def pop(self) -> Job:
        if self.is_empty():
            raise IndexError("pop from empty queue")
        return self._queue.pop(0)

    def is_empty(self) -> bool:
        return len(self._queue) == 0

    def __len__(self) -> int:
        return len(self._queue)
```

### 2. `queue/priority.py`
This module extends the core logic. It imports `Job` and `JobQueue` from `.core`.

```python
import heapq
from typing import List, Tuple
from .core import Job, JobQueue

class PriorityQueue(JobQueue):
    """A queue that pops jobs based on priority (lowest number = highest priority)."""
    def __init__(self):
        # We don't use super().__init__ because we are changing the underlying storage
        self._heap: List[Tuple[int, int, Job]] = []
        self._counter = 0  # Tie-breaker to prevent comparing Job objects directly

    def push(self, job: Job) -> None:
        # We use a counter as a tie-breaker so heapq doesn't try to compare Job objects
        heapq.heappush(self._heap, (job.priority, self._counter, job))
        self._counter += 1

    def pop(self) -> Job:
        if self.is_empty():
            raise IndexError("pop from empty priority queue")
        return heapq.heappop(self._heap)[2]

    def is_empty(self) -> bool:
        return len(self._heap) == 0

    def __len__(self) -> int:
        return len(self._heap)
```

### 3. `queue/retry.py`
This module contains the utility logic. It depends only on the `Job` definition.

```python
import time
import logging
from .core import Job

logger = logging.getLogger(__name__)

def process_with_retry(job: Job, func, max_retries: int = 3, backoff_factor: float = 2.0):
    """
    Executes a function with the given job and implements exponential backoff.
    """
    attempt = 0
    while attempt <= max_retries:
        try:
            return func(job)
        except Exception as e:
            attempt += 1
            job.retries = attempt
            if attempt > max_retries:
                logger.error(f"Job {job.id} failed after {max_retries} retries: {e}")
                raise e
            
            wait_time = backoff_factor ** attempt
            logger.warning(f"Job {job.id} failed. Retrying in {wait_time}s... (Attempt {attempt})")
            time.sleep(wait_time)
```


### Key Refactoring Improvements:
1.  **Dependency Flow**: The dependency graph is a clear DAG (Directed Acyclic Graph): `retry` $\rightarrow$ `core` and `priority` $\rightarrow$ `core`. This makes it impossible to create circular import errors.
2.  **Encapsulation**: By using `__init__.py` to export only `Job` and `JobQueue`, you hide the internal implementation details. If you decide to rename `core.py` to `base.py` later, you won't break the user's code.
3.  **Single Responsibility**:
    *   `core.py` handles data modeling.
    *   `priority.py` handles specialized sorting algorithms.
    *   `retry.py` handles error handling and timing.
4.  **Scalability**: If you wanted to add a `RedisQueue` later, you could simply add `queue/redis_backend.py` without touching the existing logic.
