<content>
To fix the race condition, we need to ensure that the "check-then-act" sequence in `process_job` is atomic. 

In the original code, two threads could both pass the `if job_id not in self.jobs` check before either has a chance to delete the job, leading to the `processor` function being executed twice for the same job.

The most efficient way to fix this is to use a `threading.Lock`. Importantly, we must **not** hold the lock while the `processor(data)` function is running, as that would prevent other threads from adding jobs or processing other jobs, effectively turning the multi-threaded queue into a single-threaded one.

Here is the corrected implementation:

```python
import threading

class JobQueue:
    def __init__(self):
        self.jobs = {}
        self.results = {}
        # A lock to protect access to the shared dictionaries
        self.lock = threading.Lock()

    def add_job(self, job_id, data):
        with self.lock:
            self.jobs[job_id] = data
        return job_id

    def process_job(self, job_id, processor):
        # 1. ATOMIC CLAIM: We use the lock to check if the job exists 
        # and remove it from the pending jobs immediately.
        # This "claims" the job so no other thread can process it.
        with self.lock:
            data = self.jobs.pop(job_id, None)
        
        # If data is None, the job_id wasn't in self.jobs (or was already claimed)
        if data is None:
            return False

        # 2. EXECUTION: Run the processor OUTSIDE the lock.
        # This allows other threads to call add_job or process_job 
        # while this thread is doing the heavy lifting.
        result = processor(data)

        # 3. ATOMIC WRITE: Re-acquire the lock to save the result.
        with self.lock:
            self.results[job_id] = result
        
        return True

    def get_result(self, job_id):
        with self.lock:
            return self.results.get(job_id)

# --- Example Usage/Test ---
if __name__ == "__main__":
    import time

    queue = JobQueue()

    def heavy_task(n):
        time.sleep(1)  # Simulate long work
        return n * n

    # Add a job
    queue.add_job(1, 10)

    # Simulate multiple threads trying to process the same job
    def worker():
        success = queue.process_job(1, heavy_task)
        print(f"Thread {threading.current_thread().name} success: {success}")

    threads = [threading.Thread(target=worker, name=f"T{i}") for i in range(3)]

    for t in threads:
        t.start()

    for t in threads:
        t.join()

    print(f"Final Result: {queue.get_result(1)}")
```

### Key Changes Made:
1.  **Introduced `self.lock`**: A `threading.Lock` object is created in `__init__` to synchronize access to `self.jobs` and `self.results`.
2.  **Atomic Job "Claiming"**: In `process_job`, I used `self.jobs.pop(job_id, None)` inside a lock. This performs two actions atomically: it checks if the key exists and removes it. This ensures that even if multiple threads attempt to process the same `job_id` simultaneously, only one will successfully retrieve the `data`; the others will receive `None`.
3.  **Fine-grained Locking**: I carefully structured the `with self.lock` blocks. By releasing the lock before calling `processor(data)`, the queue remains responsive. If we had wrapped the entire `process_job` method in a lock, the entire application would freeze whenever a job was being processed.
4.  **Thread-safe `get_result` and `add_job`**: These now also use the lock to prevent reading/writing from a dictionary while it is being mutated by another thread (avoiding `RuntimeError: dictionary changed size during iteration` in more complex scenarios).
